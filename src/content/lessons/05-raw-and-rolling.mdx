## Outcome

You can read a RAW capture, say whether Read or Read RAW suits a device you own, and explain why a used rolling code is refused.

By the end you can:

- read the sign pattern in a `RAW_Data` line as demodulator output high and low;
- set frequency and modulation before recording, and say why the Flipper needs them;
- predict from a stored counter and a window which captured values a receiver accepts, and which it ignores.

## Before you start

- **Prerequisite:** [Module 4](/learn/04-transmit). You have saved a decoded fixed-code file and seen what Send does. [Module 2](/learn/02-modulation) gave you the presets.
- **Gear:** your Flipper Zero on official firmware 1.4.3 or later. Menu paths here follow the official firmware, not a fork. A fixed-code remote you own is needed for the optional bench lab only.
- **Time:** about 60 minutes: 25 to read, 15 in the simulator and the tool picker, 20 at the bench or on the sample line.
- **Transmits:** no. Both labs only receive and read. Nothing here asks you to press Send.
- **Scope:** your own equipment, your own space, and the simulator for everything that guards a door, a gate or a car.

<Callout variant="legal" title="Own equipment only, and Send transmits">
Reading a capture is receiving. The moment you press Send on a saved file, you transmit, and that is allowed only on frequencies your region permits and only to devices you own. Do not point a replay at a car, a gate, a garage or any shared access system. Flipper's Read RAW page warns against using it with a car key fob: replaying a captured signal can de-sync the original key and leave it unusable. The [Romanian lab guide](/romania-lab-guide) sets out the three checks this course uses before any radio exercise.
</Callout>

## Understand

### When Read has no name for a signal

In Module 3, Read matched your remote to a known protocol and gave you a key. Sometimes Read stays blank while the Frequency Analyzer still shows a burst. The firmware has no decoder that fits the signal. <Flip>Sub-GHz → Read RAW</Flip> records the demodulated timings instead: every high and low stretch, with no interpretation. Flipper's documentation calls these "demodulated signals" recorded "in a RAW format".

One setting comes first. The Flipper's <Term id="cc1101">CC1101</Term> is a single-channel receiver, not a software-defined radio, so it hears only what it is tuned and demodulating for. Press <Flip>Config</Flip> on the Read RAW screen and choose the <Term id="frequency">frequency</Term> and the modulation before you press REC. On firmware 1.4.3 the modulation list is AM270, AM650 (the default), FM238 and FM476, the same presets you met in Module 2. A wrong choice records noise, and the saved file looks like a signal anyway.

Config also holds an <Term id="rssi">RSSI</Term> threshold in dBm. With a threshold set, recording pauses about one second after the signal drops below it and resumes when the signal rises again. That keeps long silences out of the file.

### What the screen is actually showing you

The Read RAW screen looks like a waveform. It is a signal-strength history. The firmware's drawing code (`subghz_read_raw.c` in 1.4.3) plots one bar per RSSI reading: something was loud, and when. It does not show pulses and gaps at microsecond scale. Those only exist in the saved file.

<div class="table-scroll">

| On the screen | What it is | What it is not |
| --- | --- | --- |
| Top line, left: `433.92` and `AM` | the frequency, and the first two letters of the preset (`AM` or `FM`) | proof that the remote uses them |
| Top line, right: `1234 spl.` | samples written to the file so far | a bit count or a key |
| Bars across the middle, labelled `RSSI` | received strength over time, with your threshold drawn as a line | the demodulated pulses |
| Buttons `Config`, `REC`, then `Stop` | set up, start, end the recording | |
| After Stop: `Erase`, `Send`, `Save` | discard, transmit once, keep | Send is the only one that transmits |

</div>

### What a RAW file holds

A saved RAW capture is a text <Term id="sub-file">.sub file</Term>. The header looks like the one from Module 4. The body is different. Here is an illustrative capture of a fixed-code remote:

```
Filetype: Flipper SubGhz RAW File
Version: 1
Frequency: 433920000
Preset: FuriHalSubGhzPresetOok650Async
Protocol: RAW
RAW_Data: 328 -456 320 -1348 980 -452 336 -444 972 -1360 340 -448
```

Flipper's file-format page defines `RAW_Data` as timings in microseconds. Values are non-zero, the line starts with a positive number, and the sign changes with every value. A line holds up to 512 values, and a long capture simply repeats the `RAW_Data:` line. There is no key and no bit count, because nothing was decoded.

A positive value is a stretch where the receiver's demodulator output was high. With an AM (OOK) preset, that means the carrier was present. A negative value is a stretch where the output was low, meaning no carrier. With an FM preset, high and low stand for the two tones. The file stores what the receiver concluded. It never stores the radio wave itself.

#### Worked example: finding the bits by hand

Take all twelve values in the sample line and sort the highs by size. Two clusters appear: 320 to 340 microseconds, about 330, and 972 to 980, about 975. The lows split the same way: 444 to 456, and 1348 to 1360. In both cases the long value is close to three times the short one. A 1:3 ratio is common in simple OOK remotes. Flipper's Princeton decoder, for example, expects a short of 390 and a long of 1170 microseconds in firmware 1.4.3. That short duration is the <Term id="te-timing-element">TE</Term> you saw in Module 4's decoded file. Read does this sorting against every protocol it knows. In a RAW file you see the raw material and do the sorting yourself. The sample here is illustrative, so do not expect it to decode.

### Read or Read RAW

The two files trade understanding for coverage.

<div class="table-scroll">

| | Decoded file (Read) | RAW file (Read RAW) |
| --- | --- | --- |
| `Protocol:` line | a name, such as `Princeton` | `RAW` |
| Content | `Bit`, `Key`, `TE` | `RAW_Data` timings |
| Size | a few lines | hundreds or thousands of values |
| Noise and gaps | gone, the decoder regenerated a clean signal | kept, a messy capture stays messy |
| Editable meaning | yes, you can read the key | no, you only see timings |
| Works for unknown protocols | no | yes, if the preset and frequency fit |

</div>

Reach for Read first. If it names the protocol, you get a compact key. Use Read RAW when Read stays blank, the Frequency Analyzer confirms a real signal, and the device is a simple one that you own. A car key fob is the wrong target.

### Fixed code and rolling code

A <Term id="fixed-code">fixed code</Term> sends the same message on every press. A copy stays valid until someone re-codes the receiver. A <Term id="rolling-code">rolling code</Term> adds a counter and a cipher. The counter goes up on each press and is encrypted, so the transmitted block changes completely every time.

<div class="table-scroll">

| | Fixed code | Rolling code |
| --- | --- | --- |
| Same message on every press | yes | no |
| A copy of one press | works until the receiver is re-coded | is spent once the receiver accepts that counter or a later one |
| What Read shows on two presses | the same `Key` | a `Cnt` value one step higher |
| Flipper's vendor table calls it | static: decode, save, play back | dynamic: decode only, save disabled |
| Examples | Princeton, Holtek, Nice FLO | KeeLoq, Nice FloR-S, Security+ 2.0 |

</div>

<Scene3D name="rolling" />

The Microchip HCS301 is the classic documented example of <Term id="keeloq">KeeLoq</Term>. Its datasheet describes a 66-bit code word. Thirty-two bits are encrypted with a 64-bit key: a 16-bit synchronisation counter, discrimination bits that let the receiver check the decryption, and the button bits. The other 34 bits travel in the clear: the 28-bit serial number, the button bits again and two status bits.

A 16-bit counter gives 65,536 values. Microchip's arithmetic: at 10 presses a day, that is nearly 18 years before a value repeats.

Flipper's supported-vendors page lists Nice FloR-S as a dynamic protocol: the remote is decoded, and "for security reasons, the save function is disabled". The firmware source agrees. In 1.4.3 the FloR-S, KeeLoq and Security+ 2.0 decoders carry no save flag, so there is no saved rolling-code file to replay. What you can see is the counter. Open a decoded FloR-S, KeeLoq or Security+ 2.0 entry in Read and its text includes a <Term id="counter-cnt">`Cnt`</Term> line, printed in hexadecimal. Press again and `Cnt` goes up. That climbing number is the clearest on-screen sign of a rolling code. A fixed code shows the same key every time, with no counter. The vendor page itself names vendors rather than ciphers. It lists Chamberlain remotes as dynamic, and the firmware's <Term id="security-2-0">Security+ 2.0</Term> decoder listens at 315 MHz.

### The acceptance window

The receiver stores the last counter it accepted. A new message is accepted only if its counter is ahead of that value and inside a forward window. Values at or behind it count as used. The HCS301 datasheet gives the typical numbers.

The single-press window exists so you can press the remote out of range and still be accepted later. Your counter climbed while the receiver's did not. When you come back, your value is ahead and inside 16, so the receiver accepts it and stores it. Storing it moves the whole window forward.

If the gap is bigger, the HCS301 decoder holds the value in a temporary slot and waits for the next sequential counter. Two presses in a row then realign it. The datasheet points out that this happens without the user noticing, because people press again when the first press fails. Anything behind the stored value falls in the blocked window and is ignored. Microchip says this window "excludes previously used, perhaps code-grabbed transmissions". The datasheet also notes that the method is a typical implementation in decoder firmware and can be changed per product, so other receivers may use other sizes.

Here is the consequence, and it is the whole lesson. The instant the receiver accepts counter 42, it stores 42. A copy of 42 is now behind the stored value and is refused. The copy is a perfect copy. It is refused because it is old.

<Callout variant="note" title="Why a replay can look like it works once">
A press the receiver never heard still has a counter ahead of the stored value. Inside a simulator that message is accepted once, and the second copy is refused. This is a model, not a method for your own gate. A real remote that has been pressed since may already have moved the counter past it, and if a copy seems to work twice, look for a second frame in the file or a receiver that changed state before you conclude anything.
</Callout>

<Callout variant="legal" title="Attacks on rolling codes stay concepts here">
Published attacks on rolling codes, the best known called jam-and-replay, try to record an unused press while stopping it from reaching the receiver. This course names them so you understand what the window is defending against. <Term id="jamming">Jamming</Term> a band is an offence in itself, and using any of this on property that is not yours is illegal. On your own gate the answer is always the same: enrol another genuine remote through the manufacturer's process.
</Callout>

### Misconceptions

- **"Read RAW records everything."** It records what the receiver demodulates at one frequency with one preset. A wrong preset gives a file full of noise.
- **"The screen shows the waveform."** It shows RSSI over time. The timings are only in the file.
- **"A blank Read means rolling code."** Flipper decodes many rolling-code remotes and shows their `Cnt`. Blank usually means an unknown protocol, the wrong preset or a weak signal.
- **"The serial number is secret."** On the HCS301 it is sent in the clear in every press. The counter is what is encrypted.
- **"A wide window revives old codes."** Every window points forward. A used value stays blocked.
- **"A refused replay advances the receiver."** Only an accepted counter is stored. A refused one changes nothing.
