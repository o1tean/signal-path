## Outcome

You can run a short keyboard script from your Flipper on your own computer, watch it type a sentence you wrote, and explain why the computer did exactly what it was told.

By the end you can:

- explain why a USB keyboard sends key positions, not letters, and why the computer trusts every one;
- read the Bad USB screen and say what USB mode, BLE mode, the layout and the connection state each mean;
- tell apart the two different Bluetooth relationships your Flipper can hold, and remove a pairing you made.

## Understand

### The computer cannot see who is typing

Plug in a keyboard and the computer asks it one question: what kind of device are you? A keyboard answers that it is a **Human Interface Device**, a HID, of the keyboard type. From then on the computer accepts a stream of keypresses and acts on each one. It cannot check whether a hand or a chip is behind them. That blind trust is the whole subject of this lesson.

Flipper's documentation describes the Bad USB app as turning the Flipper into a BadUSB device the computer detects as a HID, such as a keyboard or a mouse. The word "bad" names a class of risk, not the contents of any one script. A script can be as small as typing a sentence, which is what you will run.

When you open Bad USB, the app takes sole use of the USB port and refuses to start if qFlipper or the mobile app still holds the link, showing a "Connection Is Active" message that asks you to disconnect first (`bad_usb_app.c`, firmware 1.4.3). Close qFlipper first.

### A keyboard sends positions, not letters

Here is the detail most people miss, and the reason a script can misbehave without doing anything wrong. A USB keyboard does not send the letter `a`. It sends a number that means "the key in the position where `a` sits on a US keyboard." The USB HID Usage Tables call this a usage code. The letter key `a` is usage `0x04`, Enter is `0x28`, the left Shift modifier is `0xE1`. The computer, not the keyboard, decides what each position means, using the keyboard layout you set in your operating system.

The HID standard is explicit that the codes are positions. Its keyboard page notes that because keyboards vary by language, a vendor should reuse the closest key position rather than change the firmware: the Y key on a North American keyboard "in Germany this is typically Z," and both send the same usage code for that position. The keycaps change; the code does not.

Two consequences follow, and both show up in the lab.

- **Layout decides the letters.** If the Flipper sends codes for a US keyboard and your computer is set to a German or Romanian layout, some characters come out wrong, because the same position means a different letter. The app keeps a character-to-position map in a 256-byte `.kl` layout file on the SD card (default `en-US.kl`); the **Layout** button picks one that matches your computer.
- **Focus decides the destination.** Keystrokes go to whatever window is in front. If the wrong window has focus when the script runs, the text lands there.

A standard boot keyboard report is eight bytes: a modifier byte for Shift, Ctrl, Alt and the GUI key, a reserved byte, then up to six key positions. Typing `A` means Shift plus the `a` position. Nothing in that format says who is pressing.

### The script is DuckyScript, and small on purpose

Scripts for the Bad USB app are plain `.txt` files written in DuckyScript, the Rubber Ducky scripting language, extended by Flipper. No compilation happens; the app reads the text line by line. The commands you need here are few.

<div class="table-scroll">

| Line | What it does |
| --- | --- |
| `REM text` | A comment. The app ignores the rest of the line. |
| `DELAY 3000` | Pause once for 3,000 ms before the next line. |
| `DEFAULT_DELAY 200` | Add a 200 ms pause before every following line. |
| `STRING text` | Type the text as keypresses. |
| `STRINGLN text` | Type the text, then press Enter. |
| `ENTER` | Press the Enter key once. |
| `WAIT_FOR_BUTTON_PRESS` | Stop until you press the Flipper's button. |

</div>

The full format adds modifier keys, held keys, media keys, mouse moves and an `ID` line that sets a fake USB vendor and product identifier. You need none of them here. The point is the trust boundary, not a long payload.

### Bluetooth is a second, separate relationship

Your Flipper can speak Bluetooth Low Energy in more than one role, and the trust point is that these are different relationships, not one.

- **The mobile app link.** Pairing your Flipper with the official mobile app creates a trusted link for managing the device. It belongs to the app, not to the Bad USB feature.
- **The keyboard-over-Bluetooth link.** In BLE mode the Bad USB app advertises as a separate HID keyboard. Firmware 1.4.3 gives it its own device name (prefixed `BadUSB`) and its own stored pairing keys, kept apart from the mobile-app link (`bad_usb_hid.c`). A computer that pairs with it sees a Bluetooth keyboard, nothing more.

So "I paired my Flipper" is incomplete. Pairing it with your phone's app is not the same act as letting a computer pair with its keyboard emulation, and the two leave separate records. Record which one you enabled. In BLE mode, **Config → Remove Pairing** forgets only the bonded keyboard device.

### What the Bad USB screen is actually showing you

<Flip>Main Menu → Bad USB</Flip> lists the `.txt` files from the `badusb` folder on your SD card. Pick one to reach the run screen. The top line is the file name; below it the active layout, `(default)` for US English or the name you chose.

- The centre button reads **Run** when idle and **Stop** while running. While a script runs, the right button reads **Pause**.
- When idle in **USB mode** the right button reads **BLE** and the left reads **Layout**. In **BLE mode** they read **USB** and **Config**. Layout is a global setting, not per script.
- Before a computer is connected the screen shows **Connect to device**. Press Run first and it shows **Will run on connect** and waits.
- After a device connects, the firmware waits about 1,500 ms before the first keypress, to let the host recognise the new keyboard (`ducky_script.c`). A long `DELAY` at the top of a script does the same job more visibly.
- A malformed line shows **ERROR** with the line number, which is where reading the script first pays off.

### What a defender does about it

The host cannot tell a chip from a hand, so defence sits around the link, not in it.

- Lock your screen when you step away. A keyboard needs a session that accepts input.
- Do not plug in USB devices or cables you were handed or found, and do not accept a Bluetooth pairing you did not start.
- Check which keyboards your computer has accepted, and remove any you do not recognise.
- Read any script in full before it runs.

### Misconceptions

- **"The computer can tell the Flipper apart from a real keyboard."** It cannot. Both send the same HID usage codes over the same kind of link.
- **"The script types letters."** It types key positions. The host turns positions into letters using its layout, which is why a layout mismatch garbles the output.
- **"A safe-sounding file name makes a script safe."** The name is just text. Only reading every line tells you what it does.
- **"Pairing my Flipper with the app is the same as letting a PC use its keyboard."** They are separate BLE relationships with separate stored keys.

## Predict and practise

There is no browser tool for this yet, so the lab is on your own hardware. The first run is deliberately dull: one sentence, typed into a document you opened. The learning is in watching a device type as if it were you, then seeing what breaks when the layout or the focus is wrong.

<Lab kicker="Lab 13.1" title="Run a visible, harmless keyboard script" gear="Flipper, a computer you own, a USB-C cable, a plain-text editor. Wired; nothing transmits over the air.">

1. **Predict first.** Write down three things before you touch the Flipper: what you expect to appear in the document, what happens if a different window has focus when the script runs, and which characters, if any, come out wrong under a German layout.
2. On your computer, open a new plain-text file and save it as `signal-path-hello.txt`. Leave it empty and keep this window visible. Open a second blank plain-text window as well, saved as `wrong-window.txt`.
3. In a separate editor window, create this four-line script. Read every line, then save it as `hello.txt` (ASCII only, UTF-8 without BOM, not rich text):

   ```text
   REM Signal Path: visible typing in a document I opened
   DELAY 3000
   STRING Signal Path zy - I control this lab.
   ENTER
   ```

4. Connect the Flipper to your computer and open qFlipper. Copy `hello.txt` into the `badusb` folder on the SD card. Close qFlipper, so the Bad USB app can take the USB port.
5. On the Flipper, open <Flip>Main Menu → Bad USB</Flip> and select `hello.txt`. Confirm the screen shows **USB mode** (press the right **BLE/USB** button if it does not). Check the layout line matches your computer; in USB mode press **Layout** and pick a match if the letters would come out wrong.
6. Click into your `signal-path-hello.txt` window so it has focus. Press **Run** on the Flipper and watch both the Flipper screen and the document. Expected result: after three seconds, the sentence types itself and Enter adds a new line, with `zy` exactly as written.
7. **Control (focus):** click `wrong-window.txt` so it has focus, and no other window. Never use a terminal, browser, chat window or the script file for this step, because Enter would submit or alter what is there. Run again. Expected result: the keystrokes land in `wrong-window.txt`, not in your target document.
8. **Layout:** in USB mode press **Layout** and pick a layout that is not your computer's (a German or French one). Re-focus `signal-path-hello.txt` and run. Expected result: some characters, such as `y`, `z` or `-`, come out wrong, because the same positions mean different characters under that layout. Set Layout back afterwards.
9. Disconnect the Flipper. Delete both throwaway documents, and remove `hello.txt` from the SD card if you do not want to keep it.

</Lab>

Expected observation: identical runs, except that focus decides the destination and layout decides the letters. The Flipper sent the same key positions every time.

<Win>the sentence typed into the document you chose, the text went to `wrong-window.txt` when focus changed, and you can explain why a wrong layout produced wrong characters from the same script.</Win>

The next step is optional and uses Bluetooth, so you can feel the difference between the two pairings.

<Lab kicker="Lab 13.2" title="Pair, then unpair, the keyboard over Bluetooth" gear="Flipper and your own phone or computer; the Flipper mobile app is optional. This advertises and pairs over BLE, between your own devices only.">

1. **Predict first.** Write down whether you think the device you pair with here will also appear in the Flipper mobile app's device list, and why.
2. Close qFlipper if it is open. If you have the mobile app, check now that it connects to the Flipper, so you have a baseline.
3. Open <Flip>Main Menu → Bad USB</Flip>, select `hello.txt`, and press the right button until the screen shows **BLE mode**.
4. On your own phone or computer, open Bluetooth settings and look for a device whose name begins with `BadUSB`. Pair with it, and confirm the pairing prompt on both devices.
5. Note where this pairing appears. Compare it with the pairing your Flipper has with the mobile app. They are separate relationships with separate names. If you have no app, note that you could not compare.
6. On the Flipper, press **Config → Remove Pairing** to forget the bonded device. Confirm it has gone from your phone or computer's Bluetooth list.
7. **Control:** if you have the app, check that it still connects to the Flipper. If you have no app, write down that you could not test this.

</Lab>

Expected observation: the `BadUSB` keyboard is a distinct Bluetooth device from your Flipper's mobile-app link, with its own entry, and Remove Pairing clears only the keyboard one.

<Win>you paired and then removed the BadUSB keyboard, and you can state in one sentence how that relationship differs from pairing your Flipper with its mobile app.</Win>
