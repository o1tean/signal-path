## Outcome

You can build a small Flipper Zero app from source, run it on your own device, and explain each line from the loader's start to the Back press that ends it.

By the end you can:

- say what a <Term id="fap">`.fap`</Term> is, what its manifest declares, and why it must be built against your firmware's app <Term id="api-major">API</Term>;
- build and launch an app with <Term id="ufbt">uFBT</Term>, recording the uFBT, <Term id="sdk">SDK</Term> and firmware versions;
- trace a button press through a callback and a message queue to your main loop, and prove with the firmware's own counter that the app freed what it allocated.

## Before you start

- **Prerequisites:** [Module 0](/learn/00-setup) for the USB connection, and [Module 8](/learn/08-momentum), where you recorded your firmware's API number (87.1 on official 1.4.3). This lesson builds an app for that number.
- **Gear:** your Flipper with its microSD card, a USB-C data cable, a computer with Python 3.8 or later, and an editor. Basic C helps; every line is explained.
- **Firmware:** official 1.4.3, the current Release channel (checked 13 October 2026). On a release candidate or Momentum, see the uFBT section for the matching SDK.
- **Time:** about two hours over two or three sittings: 30 minutes to read, 30 to install and build, 60 at the device.
- **Transmits:** nothing. The app uses only the screen and the buttons.
- **Scope:** your own Flipper and your own computer. Build only code you have read.

<Callout variant="warn" title="An app can do anything the firmware exports">
Apps get no permission prompt. Firmware 1.4.3 exports 2,444 functions to apps (the `+` function rows of `api_symbols.csv`), Sub-GHz transmit and SD card access among them, and any `.fap` you start can call them. Read the source of every app before you run it. Do not flash firmware just to make an app start; change the SDK instead, and take the Module 8 backup before any firmware change.
</Callout>

## Understand

### An app is a package the loader copies into RAM

A `.fap` (Flipper Application Package) is an ELF executable with metadata and resources bundled in. It lives on the microSD card, and the processor cannot run code from the card. So the firmware's loader reads the file, checks it, copies it into RAM, fills in the address of every firmware function it calls, and jumps to its entry point.

The check is the one from Module 8. Each app records the API version it was built for, and the loader compares the **major** number with the firmware's. Official 1.4.3 declares API 87.1 in `api_symbols.csv`; the 1.5.1 release candidate declares 88.2. An app built with the 1.5.1-rc SDK shows "Outdated Firmware" on 1.4.3, however simple its code.

uFBT, the micro Flipper Build Tool, is a small Python program that downloads a prebuilt toolchain and the SDK (software development kit) for one firmware build: the headers and the list of functions apps may call. It compiles your source against them, so you never build the whole firmware. The SDK you pick decides which firmware accepts the result.

### The whole app, two files

The course app draws three lines of text and exits on Back. Make a folder named `signal_path_companion` and put these two files in it.

The manifest, `application.fam`, is a Python call that the build reads:

```python
App(
    appid="signal_path_companion",
    name="Signal Path",
    apptype=FlipperAppType.EXTERNAL,
    entry_point="signal_path_app",
    stack_size=2048,
    fap_category="Tools",
    fap_version=(1, 0),
    fap_description="A minimal on-screen companion for the Signal Path learning lab",
)
```

Only `appid` and `apptype` are mandatory. `EXTERNAL` means "build a `.fap`". `appid` (lowercase letters, digits and underscores) names the output file, `name` is what the menu shows, and `entry_point` is the C function the loader calls. `stack_size` is in bytes: too small crashes the app, too large wastes heap. `fap_category` picks the folder, so the app lands in `/ext/apps/Tools/` and appears under <Flip>Apps → Tools</Flip>.

The source, `lab_companion.c`:

```c
#include <furi.h>
#include <gui/gui.h>
#include <input/input.h>

/* This example only draws on the screen and handles the Back button. */
static void signal_path_draw(Canvas* canvas, void* context) {
    UNUSED(context);
    canvas_clear(canvas);
    canvas_set_font(canvas, FontPrimary);
    canvas_draw_str(canvas, 4, 20, "Signal Path");
    canvas_set_font(canvas, FontSecondary);
    canvas_draw_str(canvas, 4, 37, "Predict. Test. Explain.");
    canvas_draw_str(canvas, 4, 56, "Press Back to exit");
}

/* Do not block the input service: deliver events to the application's queue. */
static void signal_path_input(InputEvent* event, void* context) {
    FuriMessageQueue* queue = context;
    furi_message_queue_put(queue, event, 0);
}

int32_t signal_path_app(void* context) {
    UNUSED(context);
    FuriMessageQueue* queue = furi_message_queue_alloc(8, sizeof(InputEvent));
    ViewPort* viewport = view_port_alloc();
    view_port_draw_callback_set(viewport, signal_path_draw, NULL);
    view_port_input_callback_set(viewport, signal_path_input, queue);
    Gui* gui = furi_record_open(RECORD_GUI);
    gui_add_view_port(gui, viewport, GuiLayerFullscreen);

    InputEvent event;
    while(true) {
        if(furi_message_queue_get(queue, &event, FuriWaitForever) == FuriStatusOk &&
           event.key == InputKeyBack && event.type == InputTypeShort) {
            break;
        }
    }

    view_port_enabled_set(viewport, false);
    gui_remove_view_port(gui, viewport);
    view_port_free(viewport);
    furi_message_queue_free(queue);
    furi_record_close(RECORD_GUI);
    return 0;
}
```

Every function it calls is marked `+` (available to apps) in the 1.4.3 `api_symbols.csv`, the list the loader resolves against.

### Two threads and a queue

The three functions do not share a thread. `signal_path_app` runs on the thread the loader started for your app. The two callbacks run on the **GUI thread**: `view_port.h` marks both "called from GUI thread". Your app lends the GUI two functions and runs its own loop.

That split explains the queue. A button press reaches the GUI thread, which calls `signal_path_input`. If that callback waited, the whole screen would stall. So it copies the event into a message queue with a timeout of `0` (if the queue is full, drop the event) and returns. Your main loop sleeps in `furi_message_queue_get` with `FuriWaitForever` until an event arrives, checks it, and sleeps again. The queue holds eight events, enough for a burst of presses.

The exit test is precise. One press produces several event types, and `InputTypeShort` comes only when the button is released before the long-press threshold. Hold Back longer and you get `InputTypeLong`, then a release with no Short, so the app stays open.

### Cleanup gives back what the GUI holds first

Everything the app takes, it gives back, and the order matters in one place: the GUI must let go of the viewport before you free it. `view_port_free` checks that it is detached and crashes the Flipper on purpose if not. So the code detaches from the GUI first (disable, remove), frees the viewport, then frees the queue and closes the record. The queue and the record are independent of each other, so their order is free.

<div class="table-scroll">

| Taken at start | Given back at exit | If you forget |
| --- | --- | --- |
| `furi_message_queue_alloc` | `furi_message_queue_free` (4th) | the queue's memory is lost until reboot |
| `view_port_alloc` | `view_port_free` (3rd) | the viewport's memory is lost until reboot |
| `gui_add_view_port` | `view_port_enabled_set(false)`, then `gui_remove_view_port` (1st and 2nd) | the GUI keeps calling into an app that is gone; expect a crash |
| `furi_record_open(RECORD_GUI)` | `furi_record_close(RECORD_GUI)` (5th) | the GUI record's open count never drops |

</div>

You can check the first two rows with a number. With heap tracking on, the firmware logs a line ending in `allocation balance:`, the bytes your app thread allocated and did not free: `0` at Info level, anything else as an error. One caveat from the source: `gui_add_view_port` appends to a list inside the GUI, and if that list has to grow, the growth is charged to your thread. So the first run may read above zero for reasons that are not a leak. Record both runs and treat the second as the result; the source predicts 0 for the unmodified app, and your measurement settles it.

### What the screen is actually showing you

The display is a 128 × 64 pixel monochrome LCD. The origin `(0, 0)` is the top-left corner, x runs right and y runs down. `canvas_draw_str` places text by its **baseline**, the line letters sit on, so at `y = 20` the letters sit on row 20 and rise above it. In firmware 1.4.3, `canvas.c` gives `FontPrimary` a height of 8 pixels and `FontSecondary` 7.

### The uFBT commands you will use

`ufbt` builds the app in the current folder, with the `.fap` in `dist/`. `ufbt launch` builds, copies the file over USB, closes any running app and starts this one. `ufbt status` prints the uFBT version, the SDK version and its channel. `ufbt update --channel=release` switches the SDK to `release`, `rc` or `dev`. `ufbt cli` opens the Flipper's command line over USB.

On the first run uFBT downloads the toolchain and the SDK from the official **release** channel into `.ufbt` in your home folder; later builds reuse them. Momentum publishes an index in the same format, and `ufbt update --index-url=https://up.momentum-fw.dev/firmware/directory.json` selects its SDK. Flipper's first-app guide suggests `ufbt flash_usb` when versions disagree, which rewrites your firmware to match the SDK. In this course you change the SDK to match the firmware.

### Misconceptions

- **"A .fap is a small firmware."** It is an app the firmware loads into RAM. Firmware lives in internal flash and is replaced only by an update.
- **"Build against the newest SDK to be safe."** Newer means a higher API major, which your release firmware refuses.
- **"App logic goes in the input callback."** It runs on the GUI thread. Hand the event over and return.
